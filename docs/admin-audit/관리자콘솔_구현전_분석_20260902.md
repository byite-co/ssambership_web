## 5. 안전·권한

### 5-1. `service_role` 우회

**판정 기준·정본**: RLS 헬퍼 `is_admin()`(`baseline:1121-1131`, `users.role='admin'`, security definer). 정책 최종 상태는 `supabase/migrations/*.sql` 103본 + `contracts/snapshots/staging_contract.json`(policies 175·table_grants 129, 원장 `20260827100300`까지)으로 대조했고 아래 표 전부 일치한다. 스냅샷 이후 7본(`20260829100100`~`20260831100100`)은 대상 테이블 정책·GRANT를 바꾸지 않았다. service_role 클라이언트는 `lib/supabase/admin.ts:12-23`(키 부재 시 throw), fail-closed 래퍼 `lib/admin/adminWriteClient.ts:35-43`, 읽기 helper `lib/admin/mentorProfilesAdminRead.ts:10-16`(**테이블과 무관하게 항상 service_role 우선**, 키 없으면 세션 폴백).

분류 기호 — **A**: 대상 테이블에 `is_admin()` 정책이 이미 있거나 추가하면 세션 클라이언트로 대체 가능 · **A-2**: 정책만으로 불가 — 잠금 마이그레이션이 `authenticated`의 테이블 GRANT를 회수했으므로 GRANT 복원이 동반돼야 하고 이는 잠금 설계와 충돌(실질적으로 SECDEF RPC 전환이 정합) · **B**: service_role 불가피(RPC EXECUTE가 service_role 전용 등).

**전수 집계**: `createServiceRoleClient()` 직접 호출 **40곳**(app 6 + lib/admin 34) + `mentorProfilesAdminReadClient` 경유 **17곳**. 8/30의 "3곳"은 화면 단위 표현이었고, 실제 지점은 아래와 같다.
