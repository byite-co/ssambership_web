### 2-5. 대시보드에서 오너가 할 것 (마이그레이션 밖)

1. **소셜 제공자 3종 활성화**(Authentication → Providers): Kakao · Google · Apple — client id/secret · redirect URL. 카카오는 **이메일 scope(account_email)** 를 켤지 결정 — 미동의 가입은 DB 가 `email NULL` 로 받는다(§2-1).

3. Apple 은 최초 로그인 때만 이름을 주고 재로그인엔 이메일도 relay 주소일 수 있다 — 이름 NULL 로 가입되는 경우를 `complete_profile` 이 `p_display_name` 으로 채운다(로컬 B-1 Apple 케이스).

## 5. 오너 결정 필요 항목 — 후속 3건 반영 (2026-09-06)

### 5-1. 처리됨 (같은 PR #129 후속 커밋)

- **a. 소셜 가입 동의 원장 — 정정 C 철회(206 수정).** 이메일 가입이 남기는 원장을 실측했다: 테이블 `user_consent_records` · `consent_type` CHECK 4종(`terms` · `privacy` · `marketing` · `minor_guardian_consent`) · `consent_actor` `user`/`guardian` · `consent_version` · `is_minor` · `guardian_consent` · `source`(기본 `signup`) · `metadata` jsonb · `idempotency_key` UNIQUE NOT NULL. 운영 189행(80명) 전부 `terms`/`privacy`(+`marketing` 29) · actor `user` · source `signup` · version `legal-placeholder-2026-06-20` · metadata 키 `role/birth_date/age_gate_checked_at/verification_method` · 키 `signup:<uid>:<type>:<version>`. `complete_profile` 은 이제 `p_terms_agreed`(→ terms + privacy 행) · `p_marketing_agreed`(→ marketing 행)를 **정확히 이 모양**으로 남긴다(`is_minor` 는 생년월일 판정 · source `signup` · 같은 기본 version · 같은 멱등 키 형식 — 로컬 C-2 가 이메일 가입 행과 필드 단위로 대조). 원장 로직은 **`core_private.user_consent_signup_impl(p_user_id, p_meta, p_source)` 한 벌**: 프로비저닝 impl 이 호출(이메일 가입은 메타 그대로 · complete_profile 은 같은 키로 조립한 메타)하고, 187 트리거 함수 본문은 같은 impl 위임으로 교체했다(같은 멱등 키 → 이메일 가입은 정확히 2행 · 중복 0 · 트리거 부착 그대로 · 원문 md5 게이트 · rollback 은 CRLF 포함 원문 복원). 소셜 가입 시점엔 동의가 없으므로 원장 0행이고 완성 때 채워진다. **백필 83명은 건드리지 않았다** — 80명은 원장이 이미 있고, **관리자 3명(2026-05-01 대시보드 생성 · `users.terms_agreed_at` 도 NULL)은 terms/privacy 행이 없다**(보고만 · 채울지는 오너).
- **b. 정지 계정 개별질문 등록 차단(207 수정).** 판정을 `core_private.account_blocked_state(p_user_id) returns text` 하나로 빼고 **v2 와 v3 둘 다** AUTH_REQUIRED 직후 호출한다. v2 는 204 본문 그대로(원문 md5 게이트)에 검사 1곳만 더했고 시그니처·반환·오류 봉투·ACL 은 그대로다(rollback 은 204 원문 복원). 막는 집합 = 앱 `AccountState.isBlocked`(auth_service.dart:97-121 · account_status.dart) · 웹 `assertAccountActive`(accountStatus.ts)와 동일: `banned` · `suspended`(suspended_until NULL 또는 미래) · `deleted` · `deletion_in_progress`(`account_deletion_write_blocked` = locked~auth_soft_deleted) · `status_unknown` · `row_missing`. 만료된 정지와 탈퇴 **대기**(pending · 취소 가능 창)는 앱·DB 관례대로 통과. 오류 `ACCOUNT_BLOCKED`(P0001) · `PG_EXCEPTION_DETAIL` 에 상태값. v1 은 손대지 않았다(banned 도 통과 — 앱은 v1 을 쓰지 않는다). 로컬: 보강 전 v2 banned 통과(사전 실측) → 후 5개 상태 v2·v3 모두 차단 · 정상 학생 경로 D-1~D-5 결과 불변.
- **d. 마케팅 동의 RPC NOT NULL 결함(209 신규).** `api_web_v1.user_marketing_consent_set_self` 의 INSERT 가 `idempotency_key` 를 빼먹었다. 실측: 컬럼은 NOT NULL · UNIQUE · 기본값 없음, 원장의 다른 두 작성자(187 트리거 · 본인인증 guardian 행)는 모두 키를 명시 → **컬럼 DEFAULT 대신 RPC 가 키를 명시**(`self_rpc:<uid>:marketing:<uuid>` · 토글 이력은 호출마다 새 행). DEFAULT 를 두면 키를 빠뜨린 다른 작성자까지 조용히 통과해 "멱등 키" 의미가 사라진다. 시그니처·ACL·그 외 본문 불변 · rollback 원문 복원. 운영 `self_rpc` 행 0 · 웹·앱 호출자 0(grep) — 지금까지 한 번도 성공한 적이 없는 RPC 였다. 로컬: 모든 사용자(학생·멘토·완성 소셜 학생) on/off 왕복 · 원장 append(3행 · 키 전부 다름) · banned/JWT 없음/anon 거부.
